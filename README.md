# نظام كوفتا لإدارة الفروع والمخزون

## قبل رفع المشروع إلى GitHub

- ارفع الكود والملفات اللازمة فقط. قاعدة البيانات المحلية داخل `data/`، ملفات البيئة، الصور المستلمة عبر واتساب، والملفات المؤقتة مستثناة من Git.
- لا ترفع كلمات مرور أو مفاتيح API أو رابط قاعدة البيانات إلى المستودع. أضف القيم السرية من إعدادات الاستضافة.
- فعّل مستودعًا خاصًا إذا كانت أسماء الفروع والأصناف أو تفاصيل العمل غير معدّة للنشر العام.
- يشغّل GitHub Actions اختبارات Python الأساسية تلقائيًا مع كل رفع أو طلب دمج.
- لا يوجد مستودع Git أو رابط GitHub مربوط بهذا المجلد بعد؛ أنشئ مستودعًا واربطه من VS Code بعد مراجعة الملفات المتجاهلة.

## التشغيل

1. مع Python 3، أنشئ البيئة الافتراضية وثبّت المتطلبات مرة واحدة:

   ```powershell
   py -3 -m venv .venv
   .\.venv\Scripts\python.exe -m pip install -r .\requirements.txt
   ```

2. شغّل `start.bat` من هذا المجلد، أو نفّذ:

   ```powershell
   .\.venv\Scripts\python.exe .\server.py
   ```

3. افتح `http://127.0.0.1:8000` على نفس الجهاز.
4. عند أول تشغيل، أنشئ حساب مسؤول النظام. لا توجد كلمة مرور افتراضية.
5. من **إدارة المستخدمين** أنشئ حسابات مديري الفروع والمراقبين، ثم اربط كل مراقب بفروعه.
6. من **مخزون المخزن** سجّل الكميات الافتتاحية الفعلية قبل تجهيز أول طلبية.

لتشغيل الاختبارات محليًا: `.\.venv\Scripts\python.exe -m unittest discover -s .\tests -v`.

تُحفظ البيانات في `data/kufta.sqlite3`؛ وتشمل المستخدمين، الفروع، الطلبات، حركات المخزون، التحويلات، البلاغات، وصور الإثبات. يتضمن الكتالوج 81 صنفًا موزعة على 8 مجموعات. يتعرف النظام عند التشغيل على الأصناف الجديدة ويعطّل الأصناف القديمة التي لا تحتوي على حركات؛ الأصناف القديمة التي لها حركات تبقى ظاهرة للمحافظة على أرصدتها وسجلها. يمكن للمسؤول تنزيل نسخة من قاعدة البيانات من صفحة **حركة المخزون**.

يمكن للمسؤول إضافة أصناف ومجموعات ووحدات قياس جديدة من صفحة **الأصناف**؛ وتظهر الأصناف الجديدة مباشرةً في الطلبات والمخزون، وتبقى محفوظة بعد إعادة تشغيل النظام.

يمكن للمسؤول إضافة فرع من صفحة **الفروع**؛ يُنشأ له كود تلقائيًا ويظهر في قوائم الفروع ومحددات الحسابات والتقارير. بعد ذلك أنشئ حساب مدير الفرع من **إدارة المستخدمين** واربطه بالفرع.

## وظائف النظام

- طلب توريد متعدد الأصناف، تجهيز المخزن، تسجيل الكميات المشحونة، وتأكيد الفرع للكميات المستلمة.
- يستطيع مدير الفرع إضافة الصنف مباشرةً من الكتالوج إلى سلة الطلب، تعديل الكميات أو حذفها، ثم مراجعة الفرع والأصناف والملاحظة قبل تأكيد الإرسال للمخزن.
- يمكن لمدير الفرع رفع ملف `.xlsx` أو `.csv` لتحليله عبر OpenAI واقتراح الأصناف والكميات المطابقة للكتالوج؛ الأصناف غير الواضحة تتطلب مطابقة يدوية. لا يُنشأ الطلب ولا يُرسل للمخزن إلا بعد مراجعة المدير وتأكيده. الملف يُرسل إلى OpenAI عبر الخادم ويُحذف من مساحة ملفات الخدمة بعد التحليل.
- رصيد مخزن وفروع محسوب من سجل الحركات. يمنع النظام الصرف الذي يتجاوز الرصيد المسجل.
- يعرض مدير الفرع رصيد فرعه، ويعرض المراقب أرصدة الفروع المربوطة بحسابه مع إمكانية اختيار فرع؛ ويمكن طباعة كشف مؤرخ بالأصناف والوحدات والكميات. الكشف للعرض فقط ولا يغير الأرصدة.
- تحويل بين الفروع بمراحل الطلب، المراجعة، الإرسال، والاستلام.
- بلاغ هالك أو تست مع صورة إثبات، مراجعة المراقب، وتسجيل الهالك المرفوض كعجز في حركة المخزون.
- صلاحيات منفصلة للمسؤول ومدير الفرع والمراقب، مع حصر بيانات كل فرع وفق الحساب أو نطاق المراقب.
- تعيين كلمات المرور وإلغاؤها من الإدارة/IT فقط؛ لا يستطيع مدير الفرع تغيير كلمة مروره بنفسه.
- إشعارات داخل النظام، وسجل حركة قابل للبحث، وإدارة حسابات وتغيير كلمات المرور.
- يعرض مدير الفرع من صفحة **وارد الفرع** الأصناف والكميات التي أكد استلامها من بداية الشهر حتى اليوم افتراضيًا، مع إمكانية تعديل الفترة ومراجعة تفاصيل التاريخ والوقت ورقم الطلبية. ويعرض تقرير الرقابة افتراضيًا كل حركات الفروع التابعة، بما فيها الاستلام والصرف والتحويلات، مع رصيد بداية الفترة والوارد والمنصرف وصافي الحركة ورصيد نهاية الفترة لكل صنف. يمكن اختيار فرع وفترة محددين؛ ويقتصر التقرير على الحركات المؤكدة ضمن صلاحية الحساب. ويمكن طباعة إذن تجهيز الطلبية من سجل الطلبات، متضمنًا رقم الطلب والتاريخ والأصناف والكميات وخانات التوقيع والختم.

## نشر سحابي عبر Docker

يتضمن المستودع `Dockerfile` ومكتبة `requirements.txt` وملف `.env.example` آمنًا للمراجعة؛ ملف الإعداد لا يحتوي أسرارًا. يعمل التشغيل المحلي على SQLite، أما `KUFTA_ENV=production` فيرفض بدء التشغيل من دون `DATABASE_URL` صالح لـ PostgreSQL، لتجنب حفظ بيانات تشغيل العملاء على قرص مؤقت.

1. ادفع المشروع إلى مستودع GitHub. أبقِ بيانات الدخول وقاعدة البيانات والصور التشغيلية في الملفات المحلية؛ راجع `git status` وقائمة الملفات قبل أول رفع.
2. أنشئ خدمة Docker وقاعدة PostgreSQL مُدارة لدى مزود الاستضافة، واجعلهما في المنطقة نفسها، واربط عنوان قاعدة البيانات الداخلي بالخدمة في إعداد سري باسم `DATABASE_URL`. لا تضع عنوان الاتصال في ملفات المشروع.
3. راجع خطط الخدمة وقاعدة البيانات والتكلفة وسياسة الاحتفاظ والنسخ الاحتياطي لدى المزود قبل إنشاء موارد مدفوعة. لم يتم تثبيت خطة أو إنشاء موارد استضافة في هذا المشروع.
4. قبل تشغيل التطبيق على قاعدة الإنتاج لأول مرة، خذ نسخة احتياطية من قاعدة SQLite وتأكد من وجود PostgreSQL **فارغة**. عند تشغيل أداة النقل من جهازك، استخدم عنوان الاتصال الخارجي المؤقت للمزود، واسمح مؤقتًا باتصال عنوان IP الخاص بك فقط إن كانت المنصة تدعم ذلك. عرّف `DATABASE_URL` في جلسة آمنة واضبط `KUFTA_ENV=production` لاستخدام TLS، ثم نفّذ:

   ```powershell
   .\.venv\Scripts\python.exe .\scripts\migrate_sqlite_to_postgres.py --confirm-empty-target
   ```

   يستخدم النقل اتصال TLS في الإنتاج، ويتحقق من سلامة SQLite ومن خلوّ وجهة PostgreSQL، ويرفض الكتابة فوق أي بيانات موجودة. تُنقل المستخدمون والفروع والطلبات والأصناف وحركات المخزون وصور الإثبات والإشعارات؛ لا تُنقل جلسات الدخول، لذا سيُطلب من الجميع تسجيل الدخول من جديد. بعد النقل، أزل السماح الخارجي المؤقت واترك اتصال التطبيق عبر الرابط الداخلي فقط. ابدأ التطبيق بعد اكتمال النقل فقط.
5. أضف `KUFTA_SETUP_TOKEN` كسرّ طويل وعشوائي في إعدادات الخدمة، ثم افتح رابط الموقع عبر HTTPS وأنشئ حساب المسؤول الأول. التهيئة عن بُعد في الإنتاج تتطلب هذا المفتاح؛ لا تحفظه في المستودع ولا ترسله عبر المحادثة. يفعّل التطبيق خاصية الكوكي الآمن تلقائيًا في الإنتاج.
6. بعد التحقق من الحسابات والفرع والمخزون والتقارير والرفع والطباعة، اضبط النسخ الاحتياطي الآلي واحتفاظه ومراقبة الخدمة واستعادة نسخة احتياطية تجريبية لدى المزود. نقطة `/health` تتحقق من اتصال قاعدة البيانات، ولا تكشف أسرارًا.

يستطيع التطبيق إضافة فروع دون حدّ عددي ثابت؛ وقد جُهّز ليستقبل PostgreSQL. لكن اختيار حجم موارد الاستضافة المناسب لـ40 فرعًا وقرابة 25–37 مستخدمًا متزامنًا يحتاج اختبار حمل ببيانات واقعية ومراقبة موارد المزود قبل اعتماد الخطة. لا يعني دعم PostgreSQL وحده أن استضافة مدفوعة أنشئت أو أن سعة الإنتاج اختُبرت.

في PostgreSQL تُدار النسخ الاحتياطية من مزود قاعدة البيانات، وليس من زر تنزيل نسخة SQLite المحلي. لا تفتح قاعدة البيانات على الإنترنت العام؛ اسمح باتصال التطبيق عبر الشبكة الداخلية لدى المزود. هذا المشروع لا يتضمن حتى الآن مراجعة أمنية مستقلة أو اعتمادًا إنتاجيًا.

إشعارات SMS أو واتساب غير مفعّلة؛ تحتاج مزوّد خدمة وحسابًا معتمدًا.

لاستخدام تحليل ملفات الطلبيات، أضف `OPENAI_API_KEY` إلى إعدادات الأسرار في بيئة تشغيل الخادم؛ يمكن تحديد اسم النموذج عبر `OPENAI_MODEL` (الافتراضي `gpt-4.1-mini`). لا تضع المفتاح في ملفات المشروع أو ترسله عبر المحادثة. يرسل النظام محتوى الملف إلى OpenAI لتحليله، بحد أقصى 4 ميجابايت وبصيغة `.xlsx` أو `.csv`، ويحاول حذف الملف المرفوع بعد انتهاء التحليل. راجع سياسة الخصوصية والاحتفاظ لدى مزود الخدمة قبل استخدام بيانات تشغيل حقيقية.

طباعة الإذن تفتح نافذة الطباعة من المتصفح؛ الختم والتوقيعات تُضاف ورقيًا بعد الطباعة، ولا يدّعي النظام إصدار ختم إلكتروني أو إثبات تسليم نهائي قبل أن يؤكد الفرع الكمية المستلمة.

رفع الصورة يستخدم اختيار الكاميرا على الأجهزة التي تدعم ذلك، لكن متصفح الويب لا يستطيع إثبات أن الصورة التُقطت لحظيًا أو منع اختيار صورة سابقة.
